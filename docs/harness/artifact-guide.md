# Artifact guide

The schemas in `.rdd/schemas/` and the controller's semantic validators define machine formats. Markdown templates explain how to author readable supporting evidence. Never add ad hoc keys to a manifest whose schema disallows additional properties; put detailed narrative in linked documents.

## Specification manifest

`./rdd spec init` emits the current machine structure. Fill all required fields and validate it; an initial template is deliberately not accepted as a solution.

| Field | Meaning |
|---|---|
| `schema_version`, `id` | Format version and stable solution identity |
| `requirements_digest`, `mode`, `parent_spec_digest` | Exact requirements and prior solution relationship |
| `change_summary`, `amendment` | Why the run exists and its impact (`requirements`, `paths`, `rationale`) |
| `documents`, `decisions` | Repository-relative files that contain normative solution detail |
| `contract_files`, `generated_files` | Exact canonical and generated inventories |
| `contract_check_ids` | Checks that reproduce/compile contracts and their generated consumers before freeze |
| `project_check_ids` | Complete project-level verification obligations |
| `modules` | `id`, `requirements`, `contract_paths`, `owns_paths`, `depends_on` |
| `scenarios` | `id`, `requirements`, `kind`, `description`, `expected`, `check_ids` |
| `checks` | Bounded commands, platform scope, RED pattern, benchmark metrics, and host profile |
| `requirement_map` | Every requirement linked to `specifications` and `scenarios` |

Use supported scenario kinds (`golden`, `negative`, `boundary`, `failure`, `benchmark`, `architecture`, `accessibility`, `security`, `manual`). Concurrency and interruption details belong in descriptions and linked scenario documents; select the most appropriate supported kind rather than inventing a schema value.

Each check declares `id`, `kind`, `argv`, `cwd`, `timeout_seconds`, `platforms`, `red_pattern`, `metrics`, and `host_profile`. Commands are argument arrays executed without shell interpolation. A command requiring a pipeline should use a reviewed repository script with explicit inputs rather than embedding an opaque shell string. A manual check uses the supported external-evidence route instead of a command that returns an invented pass.

Benchmark metrics include `name`, `statistic`, `limit`, `comparison`, `minimum_samples`, and `unit`. The narrative protocol supplies dataset, hardware, sampling, timing boundaries, and scope. The machine evaluator must actually apply those rules. Check IDs and enum labels are not substitutes for assertions.

The module array contains the enforceable dependency/path map. Detailed operation inventories, semantic invariants, atomicity, error/retry behavior, and staged availability live in frozen solution documents. Keep those linked to the corresponding module, contract, scenario, and check IDs.

## Plan manifest

`./rdd plan init` emits the schema structure bound to the frozen spec digest. Preparation completes:

- `phases`: Each has `id`, `goal`, `tasks`, `checks`, `requirements_closed`, `deliverables`, and `independent_evidence`.
- `tasks`: Each has `id`, `title`, `phase`, `category`, `requirements`, `specifications`, `depends_on`, `writes`, `checks`, `acceptance`, `scope`, `anchor`, and `reuse`.
- `verticals`: Each has `id`, `goal`, and ordered `tasks`.
- `target_paths`: Complete path inventory for the planned transition, including deletion targets that will disappear from the final tree. Describe the resulting final tree and path roles in the plan narrative.
- `shells`: Explicit `path` and safe `content` for preparation-created shells.

Task IDs have the form `T001`; phases have the form `P01`. Categories are exactly `tests`, `deletion`, `modification`, `addition`, `documentation`. Scope is `small` or `large`, informing model routing while dependency and ambiguity still guide grouping.

A task's `anchor` contains `path` and `mode` (`inline` or `sidecar`). Its `writes` is the declared application change surface, not a permission to edit arbitrary parents. An addition's `reuse` records `capability_missing`, inspected `candidates` with paths/reasons, `why_not_extend`, and `duplication_check`. Other categories can use the schema's null representation when no addition rationale is needed.

The graph determines order. `independent_evidence` explains each phase's semantic closure; it is not a self-authenticating pass. The phase reviewer tests that explanation against actual dependencies and acceptance.

## Comments, shells, and generated files

Task markers use the `RDD:P01:T001` prefix with the exact controller-generated syntax. The canonical manifest/state determines which markers should exist. `anchors verify` detects divergence; `anchors reconcile` restores missing projections. Malformed, misplaced, or duplicate markers are drift to investigate, rather than content to erase silently. Do not manually erase unresolved work.

Use inline comments in compatible editable source formats. Use sidecars for editable noncommentable files and deletion targets. Frozen contracts/generated interfaces are verified read-only inputs, not implementation write targets; assigning a sidecar does not bypass protection. Preparation shell content is scaffolding only. Do not import a placeholder module or create a half-valid manifest merely to make the target tree look complete.

A task may extend a file used by a later phase. Sealing a phase preserves its accepted guarantees, not a universal prohibition on future planned edits to that path.

## Evidence, review, and digests

The controller records source commit and source digest, spec and plan digests, exact command, platform, timestamps, return code, expectation/outcome, log path/digest, origin/provenance, and benchmark metrics. A hash establishes content identity; it does not prove the logged observation was truthful.

Local evidence is produced by `./rdd check`. External platform or manual evidence is submitted with `./rdd check import FILE` using the evidence schema and explicit provenance. Preserve the actual CI/run identity, observer/environment, and raw logs required by the schema/controller. Do not manufacture absent results or reclassify a skipped check as success.

Independent review JSON contains `schema_version`, `phase`, `source_commit`, `source_digest`, `model`, `reviewer`, `session_id`, `decision`, `summary`, `checks_reviewed`, and `findings`. Decisions are `pass` or `changes_requested`. Findings contain `id`, `severity`, `requirements`, `tasks`, `path`, `message`, and `evidence`. Record current unresolved findings; describe previous findings and their verified resolution in the summary or linked notes. A review from a different candidate revision is stale.

The source digest excludes transactional runtime, evidence, and the generated active-run locator so that creating a receipt does not invalidate its own candidate. Executable code, build configuration, and policy source remain in the reviewed inventory. Follow the controller's inventory rather than inventing ignore rules. Keep tested source committed before acceptance gates.

Ignored runtime/evidence files are still critical work products. Preserve them when moving the working repository between machines or archive a completed run as described in the README. Git alone does not transfer ignored receipts. Historical baseline copies retain design history; they are not a substitute for full check logs.

## What belongs outside manifests

Keep long explanations, dependency research, benchmark protocols, diagrams, and operations in linked frozen documents. Keep secrets, user databases, private task content, arbitrary web-page dumps, and abandoned conversational instructions out of canonical artifacts. Keep implementation-specific working notes in bounded runtime packets, with links back to authority.

The harness cannot create meaningful tests merely by parsing prose. The agents author testable solution and plan artifacts; independent review and actual execution check the claims. Schema validation catches structure and consistency, while semantic completeness requires reasoning and evidence.
