# Artifact guide

The schemas in `.rdd/schemas/` and the controller's semantic validators define machine formats. Markdown templates explain how to author readable supporting evidence. Never add ad hoc keys to a manifest whose schema disallows additional properties; put detailed narrative in linked documents.

## Specification manifest

`./rdd spec init` emits the current version 3 machine structure. Fill all required fields and validate it; an initial template is deliberately not accepted as a solution. Historical version 1/2 artifacts are inspect/export inputs, never substitutes for current readiness and review evidence.

| Field | Meaning |
|---|---|
| `schema_version`, `id` | Format version and stable solution identity |
| `requirements_digest`, `mode`, `parent_spec_digest` | Exact requirements and prior solution relationship |
| `change_summary`, `amendment` | Why the run exists and its impact (`requirements`, `paths`, `rationale`) |
| `documents`, `decisions` | Repository-relative files that contain normative solution detail |
| `contract_files`, `generated_files` | Exact canonical and generated inventories |
| `domain_inventory` | Canonical S1 `path`, exact `sha256` and accepted `s1_output_digest`; the inventory is included in `documents` and the specification freeze |
| `boundary_bindings` | One row per S1 interaction with exact `interaction` ID and exclusive `operations`, `types` or composition `exports`; omitted `exports` means none for existing call/type rows |
| `contract_index_path`, `shared_generated_files` | Descriptor-derived index in existing generator metadata, and explicit ownership/purpose of shared generated support files |
| `contract_check_ids` | Specification qualification checks using disposable providers/consumers, separate from future application conformance |
| `project_check_ids` | Complete project-level verification obligations |
| `modules`, `solution_elements` | Functional subdomains, operation/invariant ownership, behavior type, reciprocal requirement/scenario links and normative references |
| `target_tree` | Complete folder/artifact design: path, kind, owner, purpose and disposition |
| `environments`, `resources` | Host/platform profiles and required tool, repository, host and external evidence resources with version/probe references |
| `scenarios` | Requirement and solution-element links, kind, preconditions, fixture, stimulus, expected oracle, verification method and check IDs |
| `checks` | Bounded commands, complete environment/resource needs, RED pattern, benchmark metrics and host profile |
| `requirement_map` | Every requirement linked to `specifications` and `scenarios`, with exact reciprocal coverage |
| `author_sessions` | Actual registered artifact authors, disjoint from approving reviewer sessions |

Use supported scenario kinds (`golden`, `negative`, `boundary`, `failure`, `benchmark`, `architecture`, `accessibility`, `security`, `manual`). Concurrency and interruption details belong in descriptions and linked scenario documents; select the most appropriate supported kind rather than inventing a schema value.

Each check declares its complete executable/evidence contract, including `id`, `kind`, `argv`, `cwd`, `timeout_seconds`, `platforms`, `red_pattern`, `metrics`, `host_profile`, `environments` and `requires`. Commands are argument arrays executed without shell interpolation. A command requiring a pipeline should use a reviewed repository script with explicit inputs rather than embedding an opaque shell string. A manual check uses the supported external-evidence route instead of a command that returns an invented pass.

Benchmark metrics include `name`, `statistic`, `limit`, `comparison`, `minimum_samples`, and `unit`. The narrative protocol supplies dataset, hardware, sampling, timing boundaries, and scope. The machine evaluator must actually apply those rules. Check IDs and enum labels are not substitutes for assertions.

The module array contains the enforceable dependency/path map. Each functional subdomain has a distinct owner module; supporting modules remain explicit and cannot own business invariants. Modules declare `contract_package`, `provided_services`, `consumed_operations`, `provided_types`, `consumed_types`, `generated_paths`, `public_exports`, `adapter_error_specs`, `qualification_checks` and `implementation_checks`. Each public export records `symbol`, owned source `path`, `kind`, descriptor `binding` (null for construction/wiring), and normative `specifications`. Composition binds these exports under the [canonical boundary policy](../../.agents/skills/domain-boundaries/SKILL.md#required-artifact); it grants no business-operation or storage access. Domain contract packages are separate within the shared generated crate. Start with private implementations inside shared crates; dependency or independent-build isolation must justify a separate implementation crate. Qualification groups cover disposable provider/consumer, negative signature, dependency direction and compatibility proofs; implementation groups cover real provider/consumer, dependency direction, compatibility and semantics. Detailed atomicity, error/retry behavior and adapter mappings live in linked frozen sections. Private implementation submodules do not need artificial standalone contracts.

Operation solution elements link through `contract_operations` to fully qualified methods. The generated `contract_index` inside `gen/rust/.rdd-generated.json` derives services, methods, message/enum types, source imports, Rust symbols and binding paths from descriptors and Prost names. It is generated evidence, never a second handwritten schema. Shared support/message files have explicit purposes. Reject unexplained operations, unowned bindings and inconsistent consumer/dependency links. Every FR and positive operation has golden coverage; every golden scenario references an FR. Schema/link completeness still requires independent semantic review.

## Refinement records

The coordinator follows [rdd-spec-grill](../../.agents/skills/rdd-spec-grill/SKILL.md) for the conversation. `./rdd spec refine FILE` consumes a version 1 JSON envelope with `schema_version`, `operation`, `session_id` and `record`. This extends the existing run state and audit trail; specification and plan formats remain version 3. Use the controller for updates rather than editing runtime state or the snapshot.

| Operation | Record |
|---|---|
| `question` | `id`, `revision`, `previous_revision`, `issue`, `material: true`; optional `sources`, `requirements`, `nodes`, `status` (`open`, `resolved`, `deferred`), `options` (`id`, `text`), `recommended_option` (displayed option ID or null), `disposition`, `decision` (`id`, `revision`) and `finding` |
| `decision` | `id`, `revision`, `previous_revision`, `statement`, `provenance`; optional `sources`, `requirements`, `nodes` and `prerequisites` (decision `id`, `revision`) |
| `publish` | `decision` (`id`, `revision`), publication `revision`, `previous_revision`, canonical `path`, exact `text` and `scenarios` |

First revisions use `previous_revision: null`; later revisions name the previous revision. Retain accepted history rather than overwriting it. Publication revisions form one sequence per decision ID and retain the file hash observed at publication. The unique exact canonical statement remains current when another section changes; the candidate inventory separately binds complete file bytes. Resolve an answered question through its next revision referencing the accepted decision. Scope uses existing requirement and workflow-node IDs; unmapped material concerns remain blocking. `sources` use repository `path` and `sha256`; an optional unique `text` excerpt binds the digest of that UTF-8 excerpt instead of the entire file. Use excerpt bindings when an author also writes elsewhere in the governing file, so its unchanged input stays valid.

Decision provenance records one actual authority source:

| `kind` | Required evidence |
|---|---|
| `choice` | `question`, question `revision`, `option`, `turn`, actual reply `text`, `qualifications` |
| `direct` | Actual `turn`, direction `text`, `qualifications` |
| `inherited` | Governing `path`, `sha256` of the unique excerpt, and exact `text` |
| `delegated` | `authority` source reference, authorized `scope`, and `rationale` |

The controller checks structural references and freshness. It cannot authenticate actor labels or establish semantic equivalence between different prose; the coordinator preserves the actual meaning and semantic review checks it. A bare ambiguous answer remains unresolved. Qualifiers must appear in the operative statement; publication requires that exact statement in the canonical file and linked scenarios covering its requirements. A matching active artifact-owner claim must authorize the publishing session and path.

`status.refinement` exposes unresolved questions, unpublished and stale decisions, and closure identity separately from readiness. Accepted-but-unpublished decisions survive restart but cannot close clarification. A question that references a reviewer finding uses that finding's resolution from the existing review stream.

The S6 owner prelists `docs/specs/refinement.json` in `documents` and its write claim, then invokes `./rdd spec snapshot --session-id ID`. A changed material closure makes the completed S6 snapshot stale even when its scoped decision inputs are unchanged. Reclaim S6 through `workflow next` and `workflow claim`, retaining every prior S6 output path, including recorded deletions; regenerate and record the snapshot, then renew S7 qualification and both final review perspectives. Normal ownership, review, lease and attempt limits still apply. Materialization validates current inputs before writing its output atomically. The versioned snapshot binds accepted decisions/publications, governing question sources, requirements, policy and current closure state; it contains no transcript or separate approval. Candidate, validation, readiness and freeze compare it with current durable state. Mutating CLI commands share the existing operation lock so refinement and freeze cannot interleave. Snapshot/review/freeze bookkeeping is excluded from what the snapshot certifies, avoiding circular identity. Late material concerns require current closure and renewed affected evidence; post-freeze changes use a new amendment run.

## S1 domain inventory

S1 alone authors `docs/specs/domain-inventory.json` under the version-2 schema. Its input digest, ownership, behavior/invariant allocations and polarity follow [domain-boundaries](../../.agents/skills/domain-boundaries/SKILL.md#required-artifact). Interaction behavior references remain IDs. S6 preserves the accepted handoff; old inventories are not migrated into active runs.

S3 alone authors `docs/specs/scenarios.json`: a complete array using the `scenarios` property of `spec.schema.json`, including assertion fields and planned check IDs. S3 validates identities, per-edge requirement overlap, allocation coverage and reciprocal FR/golden coverage before recording. S6 includes the file in `documents`, preserves its accepted hash and exact rows, and supplies the declared executable checks. Structural validation cannot prove assertion meaning; [semantic review](../../.agents/skills/phase-review/SKILL.md#specification-and-preparation-reviews) remains required. Corrections go to the original owner, preserving budgets and history.

## Plan manifest

`./rdd plan init` emits the draft bound to the frozen spec digest. P0–P4 preserve separate immutable notes; P5 alone assembles the plan. Preparation completes:

- `phases`: Each has `id`, `goal`, `tasks`, `checks`, `requirements_closed`, `deliverables`, and `independent_evidence`.
- `tasks`: Fully hydrated objective and instructions, solution-element/scenario/spec links, dependencies, exact writes, input/output resources, acceptance/checks, phase/category/scope, reuse rationale, and primary/secondary `sites`.
- `verticals`: Each has `id`, `goal`, and ordered `tasks`.
- `target_paths`: Exact path inventory implementing the frozen target tree, including deletion targets that will disappear. Every frozen file marked add/modify/delete must appear here and in task writes; retained/generated files and directories are handled separately. Preparation resolves files; it does not invent new architectural owners.
- `element_coverage`: Implementation and verification ownership for every frozen solution element, or verified preserved-baseline evidence.
- `boundary_proofs`: One row per interaction/consumer/provider and exactly one `operation` or composition `export`, with `first_phase`, `checks`, provider/consumer/verification task IDs. Operation proofs also require adapter tasks; composition proofs omit them. Empty composition `provider_tasks` requires an existing baseline repository resource for the exact export source, consumed by provider checks. Every consumer needs owned source/task/check coverage. Checks run at actual first delivery and remain cumulative.
- `type_import_proofs`: Per-interaction consumer/provider/`type` coverage, with `first_phase`, `checks`, consumer tasks and verification tasks. Imported data needs source and compilation coverage, without fabricated operation/provider tasks.
- `resource_producers`, `resource_uses`: Where every input comes from and when it is required: preparation, task RED/completion, phase or project acceptance.
- `shells`: Explicit `path` and safe `content` for preparation-created shells.

Task IDs have the form `T001`; phases have the form `P01`; verticals use `V01`; work-site IDs use `A01`. Categories are exactly `tests`, `deletion`, `modification`, `addition`, `documentation`. Scope is `small` or `large`, informing model routing while dependency and ambiguity still guide grouping.

A task's `sites` identify each work location: stable ID, target path, inline/sidecar mode, placement, primary flag and local instructions. Exactly one is primary and every declared write has a site. Placement is append, before or after an exact unique context selector; use append only where the file as a whole is the intended work location. Initial projection rejects ambiguous or missing context. A completed-task repair may append the unchanged packet at its declared site when its original selector was consumed; ambiguity still fails. The recorded repair event authorizes recovery after interruption, and reopening preflights all sites before saving state.

`writes` is the exact change surface, not permission to edit arbitrary parents. An addition's `reuse` records the missing capability, inspected candidates, why extension is insufficient and the duplication check. Shared resources retain one producer and explicit ordering. Self-produced test bootstrap resources are available only after the test task authors them, before its RED run; an empty shell is never evidence of an implemented capability.

The generated implementation matrix derives requirement/specification/element/operation/scenario/vertical/check links from these records. Module-local checks require owned source and due task/phase coverage independently of interaction proofs.

The graph determines order. `independent_evidence` explains each phase's semantic closure; it is not a self-authenticating pass. The phase reviewer tests that explanation against actual dependencies and acceptance.

## Comments, shells, and generated files

Task markers use `RDD:<phase>:<classification>:<verticals>:<task>:<site>`, such as `RDD:P01:tests:V01+V03:T001:A01`. Memberships are sorted from the canonical vertical graph. One strict parser distinguishes definition lines from examples and cross-references. The full primary packet is generated from the canonical task; secondary packets contain local scope and a primary reference. `anchors verify` detects missing, duplicate, changed or misplaced metadata and packet content, not merely a marker count. Reconciliation cannot bless an edited task instruction.

Use inline comments beside the intended work in compatible editable sources. Use deterministic adjacent sidecars for noncommentable files and deletion targets; leave absent JSON/binary/lock targets absent. Reject sidecar collisions. Frozen contracts/generated interfaces are read-only references and cannot be task writes. Preparation shells contain no executable behavior; do not import a placeholder into an otherwise required build or create a half-valid manifest to reserve a path.

Materialization preflights all sites and is resumable without duplicated packets or clobbered user changes. Controller task completion removes all of that task's packets; it does not remove other tasks or arbitrary lines containing marker-like text. A missing packet alone cannot establish task completion.

A task may extend a file used by a later phase. Sealing a phase preserves its accepted guarantees, not a universal prohibition on future planned edits to that path.

## Evidence, review, and digests

Use the [evidence guide](evidence-guide.md) for check receipts, imports, exact-candidate readiness/reviews, golden execution results and retention. The [workflow guide](workflow-guide.md) defines live findings, bounded claims and gate transitions. Use the [live-review schema](../../.rdd/schemas/live-review.schema.json) for progress reports. Final approval references the current live-review cursor; progress reports and submitted `passed` flags cannot substitute for controller evidence.

The source inventory includes Git-tracked and nonignored untracked files, excluding transactional runtime, evidence and the generated active-run locator. Governing refinement sources must be present in that inventory before affected work can be claimed. Capture may retain accepted direction while its source awaits inclusion; a rejected claim records no attempt. Deliberately include the source in Git or revise the reference to an included source, then retry. Do not force-add secrets or runtime receipts. Existing historical claims use their recorded inventories rather than today's ignore rules.

Preserve ignored evidence as described in [artifacts and retention](evidence-guide.md#artifacts-and-retention). Historical baseline copies retain design history; they do not replace full check logs. Keep tested source committed before acceptance gates.

## What belongs outside manifests

Keep long explanations, dependency research, benchmark protocols, diagrams, and operations in linked frozen documents. Keep secrets, user databases, private task content, arbitrary web-page dumps, and abandoned conversational instructions out of canonical artifacts. Keep implementation-specific working notes in bounded runtime packets, with links back to authority.

The harness cannot create meaningful tests merely by parsing prose. The agents author testable solution and plan artifacts; independent review and actual execution check the claims. Schema validation catches structure and consistency, while semantic completeness requires reasoning and evidence.
