# Artifact guide

The schemas in `.rdd/schemas/` and the controller's semantic validators define machine formats. Markdown templates explain how to author readable supporting evidence. Never add ad hoc keys to a manifest whose schema disallows additional properties; put detailed narrative in linked documents.

## Specification manifest

`./rdd spec init` emits the current version 2 machine structure. Fill all required fields and validate it; an initial template is deliberately not accepted as a solution. Historical version 1 artifacts are inspect/export inputs, never substitutes for current readiness and review evidence.

| Field | Meaning |
|---|---|
| `schema_version`, `id` | Format version and stable solution identity |
| `requirements_digest`, `mode`, `parent_spec_digest` | Exact requirements and prior solution relationship |
| `change_summary`, `amendment` | Why the run exists and its impact (`requirements`, `paths`, `rationale`) |
| `documents`, `decisions` | Repository-relative files that contain normative solution detail |
| `contract_files`, `generated_files` | Exact canonical and generated inventories |
| `contract_index_path`, `shared_generated_files` | Descriptor-derived index in existing generator metadata, and explicit ownership/purpose of shared generated support files |
| `contract_check_ids` | Specification qualification checks using disposable providers/consumers, separate from future application conformance |
| `project_check_ids` | Complete project-level verification obligations |
| `modules`, `solution_elements` | Functional subdomains, operation/invariant ownership, behavior type, reciprocal requirement/scenario links and normative references |
| `target_tree` | Complete folder/artifact design: path, kind, owner, purpose and disposition |
| `environments`, `resources` | Host/platform profiles and required tool, repository, host and external evidence resources with version/probe references |
| `scenarios` | Requirement and solution-element links, kind, preconditions, fixture, stimulus, expected oracle, verification method and check IDs |
| `checks` | Bounded commands, complete environment/resource needs, RED pattern, benchmark metrics and host profile |
| `requirement_map` | Every requirement linked to `specifications` and `scenarios`, with exact reciprocal coverage |
| `author_sessions` | Actual registered artifact authors, disjoint from approving reviewer sessions |

Use supported scenario kinds (`golden`, `negative`, `boundary`, `failure`, `benchmark`, `architecture`, `accessibility`, `security`, `manual`). Concurrency and interruption details belong in descriptions and linked scenario documents; select the most appropriate supported kind rather than inventing a schema value.

Each check declares its complete executable/evidence contract, including `id`, `kind`, `argv`, `cwd`, `timeout_seconds`, `platforms`, `red_pattern`, `metrics`, `host_profile`, `environments` and `requires`. Commands are argument arrays executed without shell interpolation. A command requiring a pipeline should use a reviewed repository script with explicit inputs rather than embedding an opaque shell string. A manual check uses the supported external-evidence route instead of a command that returns an invented pass.

Benchmark metrics include `name`, `statistic`, `limit`, `comparison`, `minimum_samples`, and `unit`. The narrative protocol supplies dataset, hardware, sampling, timing boundaries, and scope. The machine evaluator must actually apply those rules. Check IDs and enum labels are not substitutes for assertions.

The module array contains the enforceable dependency/path map. Each architectural module links to a functional subdomain covering all allocated FRs and declares `provided_services`, `consumed_operations`, `generated_paths`, `adapter_error_specs`, `qualification_checks` and `implementation_checks`. Qualification groups cover disposable provider/consumer, negative signature, dependency direction and compatibility proofs; implementation groups cover real provider/consumer, dependency direction, compatibility and semantics. Detailed atomicity, error/retry behavior and adapter mappings live in linked frozen sections. Private implementation submodules do not need artificial standalone contracts.

Operation solution elements link through `contract_operations` to fully qualified methods. The generated `contract_index` inside `gen/rust/.rdd-generated.json` derives services, methods, source imports, Rust symbols and binding paths from descriptors and Prost names. It is generated evidence, never a second handwritten schema. Shared support/message files have explicit purposes. Reject unexplained operations, unowned bindings and inconsistent consumer/dependency links. Every FR and positive operation has golden coverage; every golden scenario references an FR. Schema/link completeness still requires independent semantic review.

## Plan manifest

`./rdd plan init` emits the schema structure bound to the frozen spec digest. Preparation completes:

- `phases`: Each has `id`, `goal`, `tasks`, `checks`, `requirements_closed`, `deliverables`, and `independent_evidence`.
- `tasks`: Fully hydrated objective and instructions, solution-element/scenario/spec links, dependencies, exact writes, input/output resources, acceptance/checks, phase/category/scope, reuse rationale, and primary/secondary `sites`.
- `verticals`: Each has `id`, `goal`, and ordered `tasks`.
- `target_paths`: Exact path inventory implementing the frozen target tree, including deletion targets that will disappear. Preparation resolves files; it does not invent new architectural owners.
- `element_coverage`: Implementation and verification ownership for every frozen solution element, or verified preserved-baseline evidence.
- `boundary_proofs`: One row per descriptor operation, identifying `module`, fully qualified `operation`, `first_phase`, `checks`, and provider, consumer, adapter and verification task IDs. Ownership must cover that operation; checks remain cumulative after its first-due phase.
- `resource_producers`, `resource_uses`: Where every input comes from and when it is required: preparation, task RED/completion, phase or project acceptance.
- `shells`: Explicit `path` and safe `content` for preparation-created shells.

Task IDs have the form `T001`; phases have the form `P01`; verticals use `V01`; work-site IDs use `A01`. Categories are exactly `tests`, `deletion`, `modification`, `addition`, `documentation`. Scope is `small` or `large`, informing model routing while dependency and ambiguity still guide grouping.

A task's `sites` identify each work location: stable ID, target path, inline/sidecar mode, placement, primary flag and local instructions. Exactly one is primary and every declared write has a site. Placement is append, before or after an exact unique context selector; use append only where the file as a whole is the intended work location. Selectors are interpreted during initial projection and fail on ambiguous or missing context.

`writes` is the exact change surface, not permission to edit arbitrary parents. An addition's `reuse` records the missing capability, inspected candidates, why extension is insufficient and the duplication check. Shared resources retain one producer and explicit ordering. Self-produced test bootstrap resources are available only after the test task authors them, before its RED run; an empty shell is never evidence of an implemented capability.

The graph determines order. `independent_evidence` explains each phase's semantic closure; it is not a self-authenticating pass. The phase reviewer tests that explanation against actual dependencies and acceptance.

## Comments, shells, and generated files

Task markers use `RDD:<phase>:<classification>:<verticals>:<task>:<site>`, such as `RDD:P01:tests:V01+V03:T001:A01`. Memberships are sorted from the canonical vertical graph. One strict parser distinguishes definition lines from examples and cross-references. The full primary packet is generated from the canonical task; secondary packets contain local scope and a primary reference. `anchors verify` detects missing, duplicate, changed or misplaced metadata and packet content, not merely a marker count. Reconciliation cannot bless an edited task instruction.

Use inline comments beside the intended work in compatible editable sources. Use deterministic adjacent sidecars for noncommentable files and deletion targets; leave absent JSON/binary/lock targets absent. Reject sidecar collisions. Frozen contracts/generated interfaces are read-only references and cannot be task writes. Preparation shells contain no executable behavior; do not import a placeholder into an otherwise required build or create a half-valid manifest to reserve a path.

Materialization preflights all sites and is resumable without duplicated packets or clobbered user changes. Controller task completion removes all of that task's packets; it does not remove other tasks or arbitrary lines containing marker-like text. A missing packet alone cannot establish task completion.

A task may extend a file used by a later phase. Sealing a phase preserves its accepted guarantees, not a universal prohibition on future planned edits to that path.

## Evidence, review, and digests

The controller records source commit and source digest, spec and plan digests, exact command, platform, timestamps, return code, expectation/outcome, log path/digest, origin/provenance, and benchmark metrics. A hash establishes content identity; it does not prove the logged observation was truthful.

Local evidence is produced by `./rdd check`. External platform or manual evidence is submitted with `./rdd check import FILE` using the evidence schema and explicit provenance. Preserve the actual CI/run identity, observer/environment, and raw logs required by the schema/controller. Do not manufacture absent results or reclassify a skipped check as success.

Stage reviews identify `specification`, `plan` or `preparation` and the `semantic` or `execution` perspective. Use the active schema for exact fields. Register authors with `./rdd author record --stage STAGE --session-id ID`; the manifest inventory must match. Each perspective has a distinct actual reviewer session, separate from the authors. Both reviews bind the exact candidate, reference actual readiness evidence, retain finding history and independently verified resolutions, and have zero unresolved findings. A session/model assertion is provenance, not cryptographic authentication.

Live review is a separate report kind accepted by `review record`, valid while authoring is incomplete. Assign the independent reviewer at intake and preserve exact-revision findings, correction destinations and reviewer-verified resolutions in the event history. Final approval references the current review cursor. Inspect the active live-review schema rather than converting a progress report into a final approval. Workflow node records similarly contain actual assignments, bounded writes, input/output hashes and evidence; a submitted `passed` flag has no authority. Acceptance node status derives from the existing gates, and implementation node status derives from existing tasks/phases.

Implementation phase reviews retain their exact phase/source identity and actual check evidence. `review record` rejects stale candidates and invalid independence. Check results must explicitly enumerate golden scenario execution; passing an aggregate command is insufficient when required scenarios are missing, filtered or skipped.

`prepare` creates materialization artifacts and enters `preparing`. Commit/push the candidate and obtain its actual readiness/CI receipts and final two-perspective review before `gate preparation` grants `prepared`. The gate receipt is ignored runtime/evidence state bound to the committed source, not a tracked output that changes its own subject.

The source digest excludes transactional runtime, evidence, and the generated active-run locator so that creating a receipt does not invalidate its own candidate. Executable code, build configuration, and policy source remain in the reviewed inventory. Follow the controller's inventory rather than inventing ignore rules. Keep tested source committed before acceptance gates.

Ignored runtime/evidence files are still critical work products. Preserve them when moving the working repository between machines or archive a completed run as described in the README. Git alone does not transfer ignored receipts. Historical baseline copies retain design history; they are not a substitute for full check logs.

## What belongs outside manifests

Keep long explanations, dependency research, benchmark protocols, diagrams, and operations in linked frozen documents. Keep secrets, user databases, private task content, arbitrary web-page dumps, and abandoned conversational instructions out of canonical artifacts. Keep implementation-specific working notes in bounded runtime packets, with links back to authority.

The harness cannot create meaningful tests merely by parsing prose. The agents author testable solution and plan artifacts; independent review and actual execution check the claims. Schema validation catches structure and consistency, while semantic completeness requires reasoning and evidence.
