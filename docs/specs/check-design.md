# Executable verification design

The `.rdd/spec.json` check array fixes command names, platforms, budgets and metric keys. This document defines their interpretation. No future product check is claimed to pass during specification.

## Specification proofs

`C-CONTRACTS` runs the controller-supplied Buf/Prost pipeline with the pinned tools: lint/build, exact generated-source comparison, native and WASM compilation, valid service-provider proof and deliberately wrong-signature E0050 rejection. `C-CONSUMER` additionally compiles an actual generated-service caller on native/WASM and executes wire tests for optional presence, Unicode, nanosecond/negative timestamps, u64 precision, malformed protobuf and preserved unknown enums. Neither establishes domain validity.

`C-SPEC-INPUTS` verifies all pinned qualification source/lock/evidence bytes and D1/D2 distributions/oracle identities. `C-FILESYSTEM` repeats actual native publication/no-clobber/alias/interruption primitives on the reference filesystem. `C-INSTANCE` repeats native account/data-directory lease contention, nonce-bound acknowledgment and process-crash takeover primitives. `C-QUALIFICATION` repeats pinned native Turso transactions/reopen/rollback, real commit-checkpoint kills, Rust/WASM build, Tauri packaging/signing, actual packaged generated-interface invoke and denied-command check. These disposable experiments contain no Todo implementation. `contracts/qualification-inputs.json` pins all84 qualification source/lock/evidence artifacts and exact Rust/Cargo/Buf/Python versions; the trusted runner itself is frozen policy. Every runner rejects input drift; its fresh build/log/runtime data stays outside frozen source. Tool/version/source/result inventories are linked in `dependencies.md` and `filesystem-qualification.md`.

## Future automated suites

The Rust acceptance harness has a single `tests/acceptance/Cargo.toml` entry manifest and explicit test targets in the frozen commands. FUNCTIONAL tests the approved operations/invariants and native boundary conversions; QUERY uses independent Q1/D1 oracles; BACKUP uses actual selected-file adapters plus Turso; RECOVERY uses the real engine and independent ledger; LIFECYCLE tests single-instance/start/close/calendar; C-CAPACITY covers all field/count limits and complete paged results; C-PENDING verifies delayed-operation feedback/responsiveness; C-DIAGNOSTICS inspects all private-log outputs and rotation failure. No mock can be the only provider for persistence, packaging, backup publication or recovery acceptance. Parameterized suites must enumerate executed case IDs/counts; zero selected tests, ignored tests, missing executables and compilation failures cannot be behavioral RED or green acceptance.

`C-ARCH` inspects the full production source/dependency/command inventory and runs deliberately forbidden provider/consumer/import/SQL/registration fixtures against itself, proving that it rejects bypasses. The source scope includes first-party Rust UI event/state logic and generated interop identification. `C-SECURITY` checks actual ACL/CSP denial, direct invalid operation inputs, literal untrusted data, account/file/token scope and absence of release-only test hooks. Native validation is tested independently of UI feedback. Invalid semantic fields are distinct from large raw text that normalizes to a valid title/query.

`C-BUILD` executes the documented exact-version clean-checkout native/WASM/package build with committed locks and verifies deterministic contract generation. `C-HANDOFF` validates all 53 requirement mappings against complete revision-bound evidence, version/package identities, user/help/compatibility/dependency documentation and reproducible commands. These tools are test/build code created by implementation from this frozen design; their absence now is intentional and never a passing result.

## Delivered-package and human evidence

`C-PACKAGE` is an external evidence receipt for a clean local application-data profile installation and every golden functional journey in the actual delivered `.app`, with development tools unavailable to its process. All golden FR scenarios explicitly require this check in addition to automated behavior. `C-OFFLINE` runs the complete installed workload with runtime networking blocked; `C-PRIVACY` requires complete process-attributed observation and real separate-account denial. Accessibility checks are separate keyboard, VoiceOver and rendered contrast/200% text-size assessments on the packaged reference Mac. They use the controller's manual/external evidence route, not a script that prints a fabricated pass. Record human observer, exact package/revision, raw transcript/screenshots and environment.

Performance commands `tests/desktop/benchmark.py P1|P2|P3` orchestrate the pinned native Accessibility/CoreGraphics observer described in `quality.md`. The controller metric names end in `_ms`, with separate arrays and limits for launch; create/edit/complete/reopen/delete; search/status_filter/date_filter/ordering; export/restore. Payloads must provide raw samples, units, integer errors and environment metadata in the supported evaluator format. Warmups and invalidation reasons are retained separately; errors fail regardless of timing. Cumulative phase and project gates select these existing definitions through later planning, without changing acceptance meaning.

The currently recorded free-space shortfall is a future benchmark precondition failure, not a substitution of host or a skipped pass. Actual application benchmarks/accessibility/privacy are not specification-stage exit claims. The current stage exits only when real dependency/contract qualification and independent review are complete and `./rdd spec freeze` accepts the exact artifacts.
