# Preparation workflow

Enter with `./rdd workflow preparation`. The runner resumes the accepted specification run and activates native Goal execution; preparation is headless. Do not request routine conversational answers, a manual prompt or Goal activation. Missing approval or external evidence stops recoverably. Follow `AGENTS.md` for the read-only review/research bridge and writable planner dispatch; only the coordinator records returned review JSON in the existing ledger.

Read `AGENTS.md`, `docs/harness/workflow-guide.md`, and `docs/harness/artifact-guide.md`. Run `./rdd status` and `./rdd doctor`; verify that specification is frozen and its digests still match. Read the exact frozen manifests and only the solution sections required for planning.

Register every actual artifact author with `./rdd author record --stage plan --session-id ID` and keep the manifest author inventory consistent. Registration records provenance; it does not authenticate a session or replace independent work.

Follow P0–P8 with `workflow nodes`, `workflow next`, bounded claims and recorded artifact handoffs. Request `rdd_task_planner` for exclusive P1–P5 authorship: reuse, task decomposition, producers, classification, verticals, phases and work sites remain one reconciled graph. Use the existing `reuse-analysis`, `plan-verticals` and `plan-phases` procedures. `rdd_coordinator` owns the remaining controller/acceptance nodes; it cannot replace the required planner. `rdd_researcher` supplies read-only evidence. Keep a read-only `rdd_reviewer` continuously comparing planning progress against the frozen specification and contracts. Send snapshots after task research, DAG/phase decisions and materialization. Record findings and reviewer-verified corrections; final dual reviews do not substitute for this steering.

## Preserve the solution boundary

Treat requirements, frozen specification, accepted decisions, and canonical contracts as immutable inputs. A missing behavioral decision, incompatible contract, unqualified dependency, or contradictory requirement after specification freeze is a critical harness regression originating in specification. Record the detection stage, affected IDs, exact candidate and evidence immediately; stop affected execution and require a preventive-control repair and regression before a new trial. Do not turn an unresolved architecture question into an implementation task.

Inspect the existing codebase before planning. For regenerate, plan explicit replacement or removal; do not destroy an existing application merely because active specs were regenerated. For amendment, include the complete change impact closure and preserve unrelated behavior.

## Build the plan

Run `./rdd plan init` if no active draft plan exists. Populate `.rdd/plan/plan.json` using `.rdd/schemas/plan.schema.json`; keep detailed capability and operation reasoning in linked solution/plan notes.

1. **Inventory existing assets.** Map current modules, operations, database lifecycle, test fixtures, performance evaluators, observability, docs, dependency manifests, and shared files. Use `reuse-analysis` to distinguish reusable code from superficial name matches. Record concrete searched paths and rejected alternatives for every addition.
2. **Resolve the frozen target tree into exact writes.** Specification owns the complete folder system and architectural owners. Enumerate every file needed to realize it and whether it is existing, added, modified, deleted, generated, or a temporary shell. Include test runners, fixtures, tool configuration, evaluator inputs, packaging and documentation. Missing architectural homes are an upstream defect, not permission to invent them here.
3. **Create executable tasks.** Each task has a stable ID, objective, bounded implementation instructions, behavior/scenario/specification references, exact write ownership, work sites, required inputs with producers and timing, produced outputs, dependencies, category, phase, vertical membership, acceptance checks and completion evidence. Hydrate every task before freeze; no discovery or grooming is deferred to implementors. Bound work so its stated result fits an isolated lease rather than combining an entire project bootstrap and unrelated suites into one task. In a greenfield first phase, explicitly include the test/build infrastructure and minimal nonbehavioral application entry scaffold needed for a runnable real-boundary assertion in the `tests` tasks. Plan typed explicit not-implemented boundary stubs only where needed to run assertions, and plan their replacement in subsequent modification/addition tasks. Every tests task still needs behavioral RED; the scaffold is not a green-bootstrap exemption. Do not claim compilation failures are behavioral RED or place accepted product behavior in that scaffold. Categories are exactly `tests`, `deletion`, `modification`, `addition`, or `documentation`. Split mixed-category work. An addition requires a reuse analysis and why a modification cannot meet the same objective. A deletion includes all known references, compatibility effects, and preserved behavior.
4. **Identify producers and consumers.** Assign provider, consumer, adapter and verification ownership for every frozen contract operation. Schedule real conformance at its first due phase and cumulatively thereafter. Qualify future evidence-transfer mechanisms with disposable samples; future product receipts need not already exist, but inputs due now must be verified. Name capabilities each task requires and produces. Classify each prerequisite as already in the accepted baseline or produced by another task. Include build/tooling prerequisites, shared configuration changes, database migration order, UI/native registration, fixtures, benchmark evaluators, docs, and packaging. A declaration that something is a baseline capability needs repository evidence. Check availability separately at preparation, task RED/completion, phase acceptance and project acceptance. A test task may produce its own runner before its check without a false self-dependency. Every declared temporary stub needs a later replacement owner. Every behavior needs implementation and test ownership, or actual preserved-baseline evidence.
5. **Derive verticals.** Use `plan-verticals` to build the real dependency DAG and ordered paths through it. A vertical is an ordering of dependent tasks, not a synonym for frontend/backend team. A task may be shared by multiple verticals. Detect missing producers, dependency cycles, duplicate ownership, and concurrent writes to the same path.
6. **Add category barriers.** Within every phase require tests before deletion before modification before addition before documentation. If an actual prerequisite goes from a later category to an earlier category, separate phases or revise a false task split. Do not relabel an addition as modification to pass validation. Test authoring can precede absent behavior; runtime migration execution still follows its safe sequence.
7. **Derive phases.** Use `plan-phases`. Assign each phase a usable outcome, prerequisites, produced capabilities, explicit scope exclusions, all relevant tests/NFR checks, regression obligations, rollback/recovery behavior, and one PR. Every phase's acceptance must be attainable from its baseline, completed predecessors, and own tasks. No future-phase dependency may support a current acceptance claim.
8. **Construct the implementation matrix.** Link requirement → solution element → operation → scenario → task → vertical → phase → planned evidence. Include required human/platform evidence and the phase in which it must be obtained. Test and benchmark commands must have concrete assertions, datasets, and exit semantics. A command named `test` that always returns success is not an evaluator.
9. **Review all tasks from two independent perspectives.** Commit the candidate, run `./rdd plan validate` and `./rdd readiness plan`, then obtain distinct semantic-coverage and execution-readiness reviews. Walk every task and phase, including intermediate states, exact command inputs, producers, hosts, write scopes, real RED feasibility and work-site locations. Run disposable materialization and qualification probes; do not implement product behavior or count a compile failure as RED. The full spec must be covered phase by phase.
10. **Resolve and freeze.** Record reviews through the controller. Fix every finding, preserve its history, rerun affected proofs and obtain both approvals of the same current candidate before `./rdd plan freeze`. No `groomed: true` flag, generic prose approval or schema success substitutes for this evidence.
11. **Materialize every work site.** `./rdd prepare` creates only approved comment-only shells, adjacent sidecars, full primary task packets and secondary local instructions. It enters `preparing`, not `prepared`. Run `./rdd anchors verify`; inspect exact packet content, coverage and placement, not only counts. An interrupted materialization must resume through the controller without overwriting user edits.
12. **Accept the actual handoff.** Commit and push the exact materialized baseline. Run `./rdd readiness preparation`, obtain its required clean-checkout CI/native prerequisite evidence and both final review perspectives for that committed candidate. The reviewers inspect the materialized packets, matrix and actual receipts. Record them and run `./rdd gate preparation`. Only its passing result permits implementation. Preserve its accepted commit and source identity.

## Marker and shell rules

The manifest owns task state; comments are projections. Use the exact controller format `RDD:<phase>:<classification>:<verticals>:<task>:<site>`, for example `RDD:P01:tests:V01+V03:T001:A01`. Vertical membership is sorted and comes from the canonical graph. Every write has a work site; exactly one is primary. The primary embeds the complete execution packet, including relevant frozen contract identities and obligations; secondary sites embed local scope and a primary reference. Reference contract sections instead of copying whole schemas.

Place existing-code comments using a unique context selector beside the intended work. Use approved comment-only shells for new commentable code and adjacent sidecars for JSON, binaries, locks and deletion targets. Never create malformed or zero-byte noncommentable placeholders. Frozen/generated interfaces remain read-only references; sidecars cannot grant write access. Packet payloads must be safely encoded for the source format. Only reserved definition lines are markers; examples and links do not create task instances.

Removing any packet cannot complete a task. Only controller completion removes all of its projections. Verification rejects missing, changed, stale, duplicate, unknown or misplaced sites and incomplete packet contents.

## Exit conditions and blockers

The full backlog is hydrated, dependency-closed, category-compatible, independently approved and machine-valid. Every required work site has its canonical packet, every behavior has implementation/verification coverage, and the actual handoff passes `gate preparation`. Contract generation reproduces frozen bytes. No production task has been performed. No requirement, spec, or contract has changed.

If preparation exposes a frozen specification defect, record a critical harness regression with affected IDs and evidence. A planning defect found during implementation is likewise a critical escape. Missing tools or permissions remain environmental failures unless evidence shows the frozen execution design was itself defective. Never manufacture evidence or silently loosen an oracle.

Read [the preparation example](references/preparation-example.md) for a complete category-order counterexample and valid repair.
