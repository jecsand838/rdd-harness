# Specification workflow

Enter with `./rdd workflow specification`. The runner initializes or resumes the run and coordinator session. Return necessary specification questions through the typed `questions` envelope; keep actual answers in canonical decisions. Do not ask for a manual orchestration prompt or activate a Goal in this stage. Follow `AGENTS.md` for the read-only review/research bridge and writable specialist dispatch.

Read `AGENTS.md`, `docs/harness/workflow-guide.md`, and `docs/harness/artifact-guide.md`. Run `./rdd status` and `./rdd doctor`. Use the installed controller's `--help` for command syntax; follow the command sequence in the workflow guide. Load only relevant supporting skills.

Register every actual artifact author with `./rdd author record --stage specification --session-id ID` and keep the manifest author inventory consistent. Registration records provenance; it does not authenticate a session or replace independent work.

## Authority and scope

Treat `requirements/requirements.md` as the product source of truth. Preserve its exact text unless the user asks to amend requirements. A requirement marked draft may be used when the user's workflow instruction accepts that input; do not manufacture another approval gate. Resolve real ambiguity before freezing. Requirements identify obligations; specifications select mechanisms. Do not invent user features, implementation tasks, phase assignments, or production code in this stage. Specification owns the complete target folder system and functional subdomain/behavior inventory; preparation consumes those architectural decisions.

Distinguish the selected run mode:

- **Regenerate:** Begin a fresh solution baseline. Archive the prior artifacts for history, remove superseded active specifications through the controller, and derive a complete replacement. Do not silently delete the working application or user data. Replacement production changes are planned later.
- **Amend:** Read the prior sealed baseline and requirement diff. Preserve unaffected decisions and contract identities. Expand the impact closure through requirements, operations, scenarios, data migrations, modules, dependency versions, NFRs, and existing tests. An unchanged requirement can still need a new design to repair a defect; record that reason.

Read `../amend-requirements/SKILL.md` for amendment handling and `../context-integrity/SKILL.md` before loading outside material.

## Inputs and work allocation

Use the runner's recorded run; do not initialize another run when resuming. Intentional new-run mode selection remains a controller operation under the workflow guide. Run `./rdd requirements index` and `./rdd spec init` when those artifacts do not already exist. Record the requirement digest and baseline commit in the active run. Inspect repository paths, manifests, current public APIs, migrations, tests, and relevant accepted evidence. For the supplied Todo document, inspect all functional and non-functional IDs and the normative vocabulary, capacity, platform, benchmark, and verification sections; headings alone do not contain the complete obligations.

Follow controller nodes S0–S8 from `workflow nodes` and claim only eligible authoring nodes returned by `workflow next`. Record actual handoffs with `workflow record`; use the workflow guide for the fixed graph. Request exact named native writable profiles with `fork_turns="none"`, bounded source packets and declared writes:

- `rdd_domain_analyst` owns S1: subdomains, behaviors, invariants, owners and interactions.
- `rdd_verification_designer` owns S2–S4: measurable quality goals, independent golden/failure oracles, benchmarks and constraints.
- `rdd_qualification_engineer` owns S5: executable disposable dependency, compiler, provisioning, host and evidence-transfer experiments. `rdd_researcher` supplies read-only official-source evidence and advice.
- `rdd_contract_architect` owns S6: reconcile the architecture, complete target tree, canonical Protobuf bundle, bindings and solution candidate. It may advise earlier within an available author slot. Return upstream findings to the original owner; do not silently rewrite completed domain, verification or qualification handoffs.
- `rdd_coordinator` owns intake, controller qualification and freeze execution. It cannot substitute for a required specialist author.

Keep a read-only `rdd_reviewer` active from intake, comparing evolving design/contracts against requirements and steering corrections at each handoff or significant experiment. Preserve its slot alongside at most two authors; run specialist responsibilities sequentially when needed. At completion, the live reviewer may supply semantic approval if it authored no candidate artifacts; use a distinct execution reviewer in a released author slot. Both approvals require zero unresolved findings on the same candidate with current evidence. Live steering is not replaced by a final batch review.

Use the canonical profiles and their checked runtime settings. Do not claim a subagent ran if the runtime cannot create it, or silently change the required role/model. Report a capability blocker. A bounded adapter must apply the same profile instructions; requested settings are not observed backend attestation.

## Procedure

1. **Normalize obligations without rewriting authority.** Generate the requirement index using the controller. Link each statement to its original heading, revision, and acceptance text. Record global rules inherited by multiple requirements. Reject duplicate IDs and dangling references.
2. **Resolve decisions in the correct stage.** Return concise architectural or directional questions whose answers change required behavior, supported environments, public contracts, or acceptance through the runner's typed questions envelope. Research routine implementation choices autonomously. Store the actual answer, affected requirement IDs, and selected decision. Do not leave normative TBDs hidden in prose.
3. **Qualify dependencies.** Use `research-dependencies`. For this stack use the current official Rust, Tokio, Tauri v2, and embedded Turso documentation and the bundled stack skills. Verify the selected Rust UI can package with Tauri, local embedded database behavior, async integration, and generated contract interoperability. Pin exact compatible versions in the solution lock rather than copying a tutorial's unbounded latest version.
4. **Design domains from behavior.** Use `domain-boundaries`. Specify owners, invariants, responsibilities, required operations, dependencies, and boundaries. Keep framework adapters and persistence mechanics from dictating business domains. Map every functional requirement to its subdomain and positive/failure behaviors; keep invariant ownership explicit. Draft the complete target folder tree, including build, fixture, evaluator, packaging, documentation and application homes, with owners and purposes. Explain why each proposed module exists and where simpler organization was rejected.
5. **Specify complete observable behavior.** Define preconditions, postconditions, state transitions, normalization, error taxonomy, retries, cancellation, concurrency, atomicity, and relevant time semantics. Allocate all requirements to solution elements. Keep each rule authoritative in one place and link it elsewhere.
6. **Define the verification design.** Create golden paths for every functional requirement and every positive observable behavior, with exact reciprocal requirement/behavior/scenario links. Every golden scenario must reference a functional requirement. Add relevant invalid input, boundary, concurrency, interruption, regression, accessibility, and privacy cases. Define each scenario's stable ID, requirements, fixture, stimulus, observable oracle, and evidence method. A golden path alone does not establish recovery or security. For NFRs define measurable thresholds, reference environments, datasets, timing boundaries, sample counts, distributions, evaluators, and skip policy. Required unsupported platforms are blockers, not passes. For every complete check, declare required tools and exact versions, runner/input paths, host facilities, and external evidence. Name when each prerequisite is needed and how its availability will be proven. Exercise real tool provisioning and evidence transfer; a locally cached executable does not qualify a hosted runner.
7. **Design canonical Protobuf contracts.** Use `protobuf-contracts`. Give every architectural module a functional subdomain covering all its allocated FRs, owned paths, allowed dependencies, provided fully qualified services and consumed operations. Map solution operations to actual Protobuf methods; reject extra or unsupported public surface. Choose stable packages, presence, defaults and schema-owned response outcomes. Generated methods return a future of that response with no provider-defined error type. Freeze adapter decode, size, cancellation and lifecycle mappings separately. Keep field definitions in Protobuf and semantics in linked sections. Private Rust helper modules need no artificial contracts; local calls need no network or redundant serialization.
8. **Generate and qualify before freeze.** Commit canonical Protobuf sources/import closure, generated messages/traits and descriptor-derived symbol metadata, generator/configuration inputs and dependency locks. Use disposable providers and consumers to qualify every module on required targets: positive compilation and deliberate wrong request, response, signature and error-boundary rejection. Preserve exact commands, inputs, versions, host observations and raw results. Register these as specification qualification checks. Register separate real provider/consumer, dependency, registration and bypass checks for implementation; plan their future resource producers instead of requiring product code here. Qualify absent outcomes, unknown enums, defaults and presence handling. Downstream verification reproduces into disposable output and compares exact inventories and bytes; even compatible additions require a new specification run.
9. **Pressure-test the complete candidate.** Commit the candidate, run `./rdd spec validate` and `./rdd readiness specification`, then obtain both independent review perspectives. The semantic reviewer walks every requirement and behavior through its owner, contract and observable oracle. The execution reviewer walks the target layout, exact toolchain, complete check prerequisites and declared hosts, including clean-checkout provisioning and required evidence transport. Both check contradictory replicas, omitted decisions, weak assertions and unnecessary abstractions. A shape-valid manifest is not semantic approval.
10. **Resolve and re-review before freeze.** The coordinator records returned read-only review JSON through `./rdd review record FILE`. Preserve every finding and its independently verified resolution. Fix all findings, rerun affected proofs, and re-review the changed candidate until both perspectives approve the same current identity with zero unresolved findings. Runtime session/model provenance must come from actual independent work; it is not established by writing a role label into JSON. Missing evidence or exhausted controller limits leaves the workflow incomplete.
11. **Freeze exact artifacts.** `./rdd spec freeze` requires current readiness and independent review evidence, then freezes the approved inventory. Commit its outputs. Review/check/gate receipts stay outside the source inventory they certify; do not create circular review hashes or arbitrary source exclusions.

## Exit conditions

Every requirement has an explicit solution mapping and acceptance strategy. Every boundary has a canonical owner and enforceable interface. Every required NFR has a protocol, including human evidence where automation cannot substitute. The exact contract set has a successful generation/compile experiment. Both independent review perspectives are resolved for the exact candidate. The complete target tree and check execution design are frozen. The controller accepts the freeze. A frozen specification defect discovered downstream is a critical harness regression, requiring evidence, a preventive-control repair and a reproducing regression; repeated amendments are not normal progress.

If infeasible, retain the evidence and the smallest concrete decision needed from the user. Do not weaken requirements to satisfy tooling. Preparation and implementation may report blockers; they cannot retroactively resolve requirement ambiguity.

Use `.rdd/templates/specification.md`, `.rdd/templates/scenario.md`, `.rdd/templates/dependency-research.md`, and `.rdd/templates/decision.md` for human-readable artifacts. Read [the worked review example](references/specification-example.md) when translating prose into scenarios and contracts.
